# T-025 `updated_at` memakai jam database

## Status

Selesai (2026-10-10). Branch: `fix/t-025-updated-at-jam-database` (dari `master` setelah T-024).

## Ringkasan

Perbaikan test acak `notes-schema.int.test.ts` › updated_at (log T-024 › Kendala). Penyebabnya ada di `columns.ts`: `updated_at` awal diisi `defaultNow()` (jam PostgreSQL di VM Docker), sedangkan nilai setelah `update()` diisi `$onUpdate(() => new Date())` (jam host Node). Bila jam host sedikit tertinggal, `updated_at` bisa mundur, di test maupun di produksi.

- **`apps/api/src/db/schema/columns.ts`**: `updatedAt()` kini memakai `$onUpdate(() => sql\`now()\`)`. Insert dan update sama-sama memakai jam database. Perubahan ini hanya di runtime Drizzle, jadi skema dan migrasi tidak berubah.
- **`apps/api/test/int/db/schema.int.test.ts`**: test baru "updated_at dari update() Drizzle memakai now() database, bukan jam host". Di dalam satu transaksi, test:
  1. menunggu 50 ms (`pg_sleep(0.05)`);
  2. membaca `now()` yang dibulatkan ke `timestamptz(3)` sebagai ISO UTC;
  3. melakukan insert dan `update()` Drizzle;
  4. memastikan `updated_at` sama persis dengan `now()` itu dan dengan `created_at`.

  Karena `now()` tetap selama transaksi sedangkan jam host terus berjalan, `new Date()` pasti berbeda setelah jeda itu.
- **`apps/api/test/int/notes/notes-schema.int.test.ts`**: asersi `toBeGreaterThanOrEqual` dipertahankan, dengan komentar bahwa kedua nilai kini dari jam database sehingga tidak pernah mundur.
- **`docs/conventions.md`** › Database: aturan baru bahwa timestamp yang ditulis server memakai `now()` database, tidak pernah `new Date()` host. Aturan ini juga berlaku untuk `set` manual (contoh yang sudah ada: upsert di `drizzle-user-repository.ts`) dan SQL mentah, dengan rujukan ke test penjaganya.

## Keputusan yang diambil sendiri

- **`now()` dibandingkan setelah dibulatkan ke `timestamptz(3)` dan diformat `to_char` sebagai ISO UTC.** `now()` berpresisi mikrodetik, sedangkan kolom membulatkan ke milidetik. Parser tanggal JavaScript memotong, bukan membulatkan, sehingga perbandingan tanpa pembulatan yang sama bisa berbeda 1 ms. String ISO dari database juga menghindari ketergantungan pada cara driver mem-parse `tx.execute`.
- **Jeda `pg_sleep(0.05)` di dalam transaksi** agar test pasti merah dengan `new Date()`, tidak bergantung pada kebetulan selisih jam.
- **Test di `notes-schema.int.test.ts` tetap `toBeGreaterThanOrEqual`**, dengan komentar. Kedua nilai kini dari jam database, jadi asersi ini tidak lagi acak. `>=` tetap perlu karena dua penulisan bisa jatuh di milidetik yang sama.
- **Test `users` lama (nilai awal 60 detik di masa lalu) dibiarkan.** Test itu menguji `toBeGreaterThan` yang ketat dan tetap benar.
